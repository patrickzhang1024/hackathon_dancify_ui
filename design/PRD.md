# Dancify 产品需求文档（PRD）

## 0. 文档信息

| 项目 | 内容 |
| --- | --- |
| 产品名称 | Dancify（暂定） |
| 产品形态 | 浏览器端音乐分析与 AI 编舞可视化工具 |
| 文档版本 | v0.1 |
| 当前阶段 | MVP 设计与技术验证 |
| 面向对象 | 产品、UI/UX、前端、算法/LLM 开发 |

> 本文用于指导第一轮产品和 UI/UX 设计。技术方案以仓库 `plan/feasibility.md` 与 `plan/tech-stack.md` 为参考；若技术实现与本文件冲突，需在评审时记录并确认。

## 1. 产品概述

### 1.1 一句话定义

Dancify 将一首音乐转化为可理解的音乐分析报告，再基于报告生成不同的编舞方向，并在 three.js 虚拟角色上随音乐同步播放。

### 1.2 用户价值

用户不需要具备音乐分析或编舞专业知识，也可以理解一首歌的节奏、情绪、结构和能量，并快速看到这些特征如何影响舞蹈结果。

产品需要回答三个核心问题：

1. 这首音乐有什么特点？
2. 为什么系统会生成这样的舞蹈？
3. 我能否比较、调整和重新生成结果？

### 1.3 核心体验

```text
上传音乐
  → 分析音乐
  → 阅读音乐报告
  → 选择/生成编舞方向
  → 观看 3D 角色跳舞
  → 比较、调整或保存结果
```

## 2. 目标与非目标

### 2.1 MVP 目标

- 支持用户上传一首本地音频，并看到上传成功状态。
- 对音乐生成一份易懂的分析报告，至少包含节奏、情绪、结构、能量、音色、曲风六个维度中的核心结果。
- 基于报告生成至少 3 个有明确差异的编舞方向。
- 在 3D 虚拟角色上播放至少 1 套稳定、可卡拍的舞蹈脚本。
- 用户可以播放、暂停、拖动时间线和切换编舞版本。
- 在分析失败、模型加载失败或 LLM 不可用时，用户仍能获得明确反馈和可执行的下一步。

### 2.2 暂不纳入 MVP

- 用户上传自己的 3D 角色或动作捕捉数据。
- 从零生成连续人体动作或真实动捕级别的动作。
- 社交分享、公开作品广场和多人协作。
- 完整的长期用户画像和复杂推荐系统。
- 移动端原生 App。
- 复杂的专业音频编辑能力。

## 3. 目标用户与使用场景

### 3.1 主要用户

**音乐/舞蹈兴趣用户**

- 想知道一首歌适合什么类型的舞蹈。
- 希望快速获得创作灵感。
- 不熟悉 BPM、音色、MIR 等专业术语。

**编舞或内容创作者**

- 需要根据音乐快速探索多个舞蹈方向。
- 关心段落、能量、动作风格和可视化效果。
- 需要比较不同版本并保存一个方向继续创作。

**技术/创意展示用户**

- 关注 AI 如何理解音乐并转成动作。
- 主要通过 Demo 体验产品的即时反馈和视觉效果。

### 3.2 典型场景

1. 用户上传一段 20–30 秒音乐，快速查看分析结果和一个舞蹈 Demo。
2. 编舞者上传完整歌曲，比较三种不同的舞蹈方向。
3. 用户在播放过程中观察副歌、drop 等段落如何触发动作和能量变化。

## 4. 产品原则

### 4.1 先让用户看懂，再展示专业数据

默认展示自然语言结论和视觉化结果；BPM、频谱、置信度等技术细节作为证据或展开信息。

### 4.2 解释生成结果

每个编舞方向都要说明“为什么这样编排”，例如：

> 副歌能量明显上升，因此加入更大幅度的动作和跳跃片段。

### 4.3 音乐是主角，角色是结果

播放页需要让用户感受到动作由音乐驱动，而不是一个孤立的 3D 模型在播放动画。

### 4.4 关键状态始终可见

当前歌曲、分析进度、当前段落、播放状态、当前编舞版本和错误状态不能被隐藏在难以发现的区域。

### 4.5 控制复杂度

MVP 优先保证上传、分析、生成、播放这条主链路的清晰和稳定，不用过多专业控制项制造复杂度。

## 5. 核心用户流程

### 5.1 主流程

```text
[Landing / Upload]
        ↓
[Audio Uploaded]
        ↓
[Analyzing]
        ↓
[Analysis Report]
        ↓
[Choreography Directions]
        ↓
[3D Dance Player]
        ↓
[Compare / Adjust / Save]
```

### 5.2 首次使用路径

1. 用户进入首页，理解产品可以做什么。
2. 上传音频，可选填写歌词或跳过。
3. 点击“开始分析”。
4. 查看分析进度和部分已完成结果。
5. 阅读音乐摘要和六项指标。
6. 点击“生成编舞”。
7. 查看三个编舞方向并选择一个。
8. 进入播放页，查看角色随音乐跳舞。

### 5.3 返回用户路径

用户可以从首页进入最近项目，恢复上次的歌曲、报告和编舞结果。MVP 可先支持浏览器本地保存，不要求账号体系。

## 6. 页面与功能需求

## 6.1 页面一：Landing / 音乐上传页

### 页面目标

让用户在 10 秒内理解产品，并完成音频上传。

### 必须展示

- 产品名称和一句话价值主张。
- 音频上传入口。
- 支持的文件格式和大小限制。
- 可选歌词入口，并说明歌词用于情绪/主题分析。
- 一段简短的体验流程说明：分析 → 生成 → 播放。
- 最近项目入口（如果本地已有项目）。

### 主要交互

- 拖拽上传或点击选择文件。
- 上传后显示文件名、时长、格式和音频波形/占位波形。
- 用户可添加歌词文本或 LRC 文件。
- 点击“开始分析”。
- 用户未上传文件时，“开始分析”不可用，并给出明确提示。

### 设计要求

- 首屏视觉重点应体现“音乐转化为动作”，而不是普通文件上传工具。
- 上传区域需要明确可操作状态、拖拽悬停状态和错误状态。

## 6.2 页面二：Analyzing / 分析进度页

### 页面目标

降低等待焦虑，让用户理解系统正在分析什么，并为后续报告建立预期。

### 分析步骤

1. 读取并解码音频
2. 识别节奏与 BPM
3. 分析情绪与音色
4. 识别音乐段落与能量变化
5. 整理音乐分析报告
6. 准备编舞生成

### 必须展示

- 总体进度。
- 当前处理步骤和简短解释。
- 已识别的即时结果，例如 BPM、歌曲时长或当前段落。
- 预计剩余时间或“处理时间取决于设备与音频长度”的说明。
- 取消分析入口。

### 状态

- 正在分析：展示动态进度。
- 分析完成：自动进入报告页，并保留“查看报告”按钮。
- 分析失败：说明失败环节、原因和“重试/更换文件”操作。
- 用户取消：回到上传页，保留已上传文件信息。

## 6.3 页面三：Analysis Report / 音乐分析报告页

### 页面目标

把专业分析结果翻译成用户能够理解的音乐画像，并建立对编舞结果的期待。

### 页面结构

#### A. 音乐摘要

- 歌曲名、时长、BPM。
- 3–5 个整体标签，例如 `Energetic`、`Bright`、`Playful`。
- 一段自然语言摘要。
- “适合的舞蹈感觉”或“编舞建议”。

#### B. 六项指标

每个指标至少包含：

- 指标名称。
- 主要结论。
- 可视化值或等级。
- 对编舞的影响。
- 置信度或“实验性判断”标记（如果适用）。

六项指标：

| 指标 | 用户能看到的结论 | 对编舞的影响 |
| --- | --- | --- |
| 节奏 | BPM、速度、律动密度 | 步点、换招频率、切分重音 |
| 情绪 | 明亮/阴郁、平静/兴奋 | 动作质感、力度、表情 |
| 结构 | intro、verse、chorus、drop 等 | 段落编排、招牌动作 |
| 能量 | build-up、drop、decay | 动作幅度、起跳高度 |
| 音色 | 明亮/温暖、打击/和声 | 顿挫或流动、局部或全身动作 |
| 曲风 | pop、hiphop、EDM 等 | 选择动作库和舞种 |

#### C. 音乐时间线

- 展示音频波形或能量曲线。
- 标出主要段落。
- 标出副歌、drop、能量转折点。
- 支持点击段落跳转试听。

#### D. 下一步操作

- 主按钮：“生成 3 个编舞方向”。
- 次要操作：“重新分析”“编辑歌词”“返回上传”。

### 设计要求

- 默认优先展示解释，不要让用户先面对算法术语。
- 报告需要有“结论 → 证据 → 编舞影响”的层级。
- 结构识别置信度较低时，需要用合适文案表达不确定性，不能伪装成绝对准确。

## 6.4 页面四：Choreography Directions / 编舞方向页

### 页面目标

让用户理解三套方案的差异，并选择一个进入 3D 播放。

### 每个方向卡片必须包含

- 方向名称。
- 一句话概念描述。
- 舞种或动作风格。
- 能量等级。
- 复杂度。
- 身体状态偏好：站立、坐、地面、跳跃等。
- 代表动作标签。
- 与音乐的匹配理由。
- 预览入口。

示例方向名称：

- Grounded Groove：低重心、连续律动、偏街舞。
- Neon Release：高能量、跳跃、强方向变化。
- Soft Gravity：流畅、抒情、强调身体线条。

### 主要交互

- 横向比较三个方向。
- 预览某个方向的短片段。
- 选择一个方向进入播放页。
- 点击“重新生成”，生成新的方向组合。
- 如果某个方向生成失败，显示单卡片错误，不影响其他方向使用。

### 设计要求

- 三个方向必须有明显的视觉、文案和参数差异。
- 不要只用“方案 A/B/C”；名称应该帮助用户理解创意方向。
- 需要标识生成中、生成成功、生成失败三种状态。

## 6.5 页面五：Dance Player / 3D 舞蹈播放页

### 页面目标

让用户直观看到音乐、段落、动作和角色之间的关系，并能控制播放。

### 推荐布局

```text
┌─────────────────────────────────────────────┐
│ 歌曲信息 / 当前编舞版本 / 返回报告           │
├──────────────┬──────────────────┬───────────┤
│ 音乐分析摘要  │                  │ 当前动作   │
│ 段落列表      │   3D 角色舞台    │ 编舞参数   │
│              │                  │ 版本切换   │
├──────────────┴──────────────────┴───────────┤
│ 波形 / 段落 / 节拍时间线 / 播放控制           │
└─────────────────────────────────────────────┘
```

### 必须功能

- 播放、暂停、重新播放。
- 拖动时间线跳转。
- 显示当前段落和当前节拍。
- 切换三套编舞方向。
- 显示当前动作名称和身体状态。
- 显示当前 BPM、能量或段落标签。
- 进入全屏舞台模式。
- 返回分析报告。

### 可选功能（P1）

- 镜像动作。
- 调整动作幅度。
- 调整角色朝向。
- 调整舞蹈整体强度。
- 重新生成当前编舞。
- 保存项目或导出播放链接。

### 播放状态

- 加载角色：显示舞台占位和资源加载进度。
- 加载动作：显示当前动作资源状态。
- 正常播放：时间线、节拍和段落同步更新。
- 音画不同步：提示正在重新同步，不要让角色静默卡住。
- WebGL/模型失败：显示可返回报告的降级页面。

### 设计要求

- 3D 舞台是主要视觉焦点。
- 控制项不应遮挡角色关键动作。
- 播放时应有轻微但克制的节拍反馈；避免所有元素同时跳动。
- 用户应能看出动作切换与音乐段落变化之间的对应关系。

## 6.6 页面六：Recent Projects / 最近项目（P1）

### 页面目标

让用户恢复以前的分析结果，减少重复上传和等待。

### 项目卡片信息

- 歌曲名。
- 时长。
- 分析日期。
- BPM 和主要标签。
- 最近选择的编舞方向。
- 继续查看/删除操作。

MVP 可只使用浏览器本地存储，不要求登录。

## 7. 组件与交互状态清单

设计稿至少需要覆盖以下状态：

- 默认空状态。
- Hover、focus、pressed、disabled。
- 文件拖入中。
- 文件格式错误。
- 文件过大。
- 音频解码失败。
- 分析进行中。
- 分析成功。
- 分析失败和重试。
- LLM 生成中。
- 单个编舞方向生成失败。
- 3D 资源加载中。
- 3D 资源加载失败。
- 播放、暂停、拖动、切换版本。
- 无歌词。
- 歌词内容为空或格式错误。
- 浏览器不支持 WebGL。

## 8. 文案要求

### 8.1 语言风格

- 使用简洁、具体、面向用户的语言。
- 优先使用“分析音乐”“生成编舞”“播放舞蹈”等动作词。
- 不直接暴露内部模块名，例如 MIR、Agent、MotionControlScript。
- 专业数据可以展示，但必须配合自然语言解释。

### 8.2 推荐按钮文案

| 场景 | 主按钮 | 次要操作 |
| --- | --- | --- |
| 上传后 | 开始分析 | 更换文件 |
| 报告页 | 生成 3 个编舞方向 | 重新分析 |
| 方向页 | 进入播放 | 预览、重新生成 |
| 播放页 | 播放 | 暂停、切换版本、返回报告 |
| 失败状态 | 重试 | 更换文件、稍后处理 |

避免使用“提交”“执行”“运行模型”等技术化表达。

## 9. 非功能需求

### 9.1 性能

- 音频分析应在后台线程执行，避免页面明显卡顿。
- 大型模型和动作资源应支持懒加载。
- 分析期间页面可以继续响应取消和返回操作。
- 播放过程中应尽量维持稳定帧率，并以音频时间为同步基准。

### 9.2 可访问性

- 所有主要操作支持键盘访问。
- 颜色不能作为唯一状态表达方式。
- 文本和背景有足够对比度。
- 播放控制有明确的 aria-label。
- 支持减少动态效果的系统偏好。

### 9.3 隐私与安全

- 明确告知用户音频和歌词的处理方式。
- 不在 UI、日志或错误信息中展示 API key。
- 用户提供的歌词视为不可信文本。
- LLM 返回结果作为数据校验，不执行任意代码。
- 若使用浏览器端 BYO-key，需要在 UI 中明确风险提示。

## 11. MVP 验收标准

### 用户任务验收

- 新用户无需额外说明，可以找到上传入口。
- 用户可以成功上传一首支持格式的音频。
- 用户能看懂分析报告的主要结论，而不需要理解算法术语。
- 用户能区分三个编舞方向的差异。
- 用户可以进入播放页，并完成播放、暂停、拖动和切换版本。
- 播放页能显示当前段落和当前动作。
- 任意失败状态都有明确原因和下一步操作。

### 体验验收

- 从上传到看到第一套舞蹈结果的路径没有不必要的页面跳转。
- 等待过程中用户始终知道系统正在做什么。
- 报告中的音乐特征与编舞方向之间有可理解的关联。
- 3D 舞台、时间线和控制区层级清晰，不互相争夺注意力。

## 12. 设计评审问题

每次设计评审请重点回答：

1. 用户第一眼知道这是什么产品吗？
2. 用户知道下一步应该做什么吗？
3. 报告中的数据是否被翻译成了可理解的结论？
4. 三个编舞方向是否真的有差异，而不是换了颜色？
5. 用户能否理解音乐变化和动作变化的关系？
6. 等待、失败和资源加载时，界面是否仍然有明确反馈？
7. 视觉风格是否服务于音乐和舞蹈，而不是只增加装饰？

## 13. 待确认事项

- 首版支持的音频格式、大小和最长时长。
- 是否支持歌词文本、LRC 文件，或两者都支持。
- 是否需要用户输入自己的 API key，以及如何在界面中告知风险。
- 首版是否展示完整六项指标，还是先展示节奏、情绪、结构、能量四项。
- 首版默认提供一套角色和多少个动作片段。
- 三个编舞方向是串行生成还是并行生成。
- 是否需要导出视频、分享链接或下载舞蹈脚本。
- 产品最终视觉方向和品牌名称是否已经确定。

## 14. 建议的第一轮设计范围
